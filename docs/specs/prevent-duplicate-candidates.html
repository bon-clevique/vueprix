Spec: prevent-duplicate-candidates

vueprix bot の候補生成における「同一商品の繰り返し露出」と「永久に紹介しない商品の制御」を強化する設計。(1) COOLDOWN_HOURS を 24h → 720h (30 日) に延長、(2) Notion 上に「ブラックリスト DB」を新設して恒久ブロック ASIN を bon が UI から管理可能にする。追加課金ゼロ (Notion Free / Keepa Pro 範囲内)。

1. Context (背景)

運用観測 (2026-05-14 時点) で 2 つの不満が顕在化した:

  • 同じ ASIN が何度も candidate に上がる: 現状 COOLDOWN_HOURS = 24 (src/config.ts:68) で、24h 経過した posted ASIN は再度候補化される。値下げが継続している商品は cron (2h ごと、1 日 12 回) で頻繁に再ヒットし、bon が Notion で rejected しても 24h 後にまた backlog として戻ってくる。
  • 「2 度と紹介したくない商品」の管理が PR 必須で運用負荷が高い: 既存の恒久ブロックは data/blocklist.md (src/blocklist.ts) のみで、PR 作成 + merge が必要。bon が Notion UI から即時ブロックできる経路がない。

関連実装: queryDuplicateAsins (src/notion.ts:352) と readRecentAsins (src/history.ts:54) が cooldown 内 ASIN を union して activeAsins を構成 (src/run/orchestrator.ts:78-83)、loadBlocklist (src/blocklist.ts:30) が deals / fixed / brand 全経路で除外する。本 spec はこの 2 機構の パラメータ拡張 と ソース追加 でほぼ完結する小規模変更。

1.5 Glossary

COOLDOWN_HOURS
posted / rejected 以外 (backlog/doing/approved/posted) の ASIN を「直近 N 時間以内に候補化済」とみなして二重投稿を防ぐ閾値。現行 24h、本 spec で 720h (30 日) に拡張。
activeAsins
orchestrator が run 開始時に組み立てる「除外対象 ASIN 集合」。queryDuplicateAsins (Notion DB primary) ∪ readRecentAsins (post-history.jsonl secondary) で構成。本 spec では ここに queryBlacklistAsins も union する。
data/blocklist.md
既存の Markdown ベース永久ブロックリスト。git 履歴で理由が追跡可能、PR レビューに馴染む。本 spec で廃止せず併用 (二重管理ではなく「役割分離」)。
Notion ブラックリスト DB
本 spec で新設。bon が Notion UI から「2 度と紹介しない」と判断した ASIN を即時登録できる場所。schema: ASIN (rich_text, required) / 商品名 (title) / 理由 (rich_text) / 登録日 (date, auto)。
MAX_QUERY_PAGES
Notion API paging 上限 (src/config.ts:78)。現行 10 (= page_size 100 × 10 = 1,000 件)。本 spec の cooldown 拡張で queryDuplicateAsins 結果が 1,000 件に近づく可能性があるため監視ポイント。
rejected
Notion DB の Status option の 1 つ。ADR-003 で「ガイドライン残しつつ将来の再候補化を許可」と定義済。本 spec では rejected の意味を変更せず、別 DB として恒久ブラックリストを新設する (案 B)。

2. Goal

GitHub Actions cron (2h ごと) が走るたびに、次の 2 条件を満たす ASIN を 候補から除外する:

  1. 過去 30 日以内に Notion DB に作成された ASIN (Status ∈ {backlog, doing, approved, posted}) または post-history.jsonl に投稿記録のある ASIN — COOLDOWN_HOURS = 720 で実現
  2. Notion ブラックリスト DB に登録された ASIN (登録時期問わず恒久) — 新規 queryBlacklistAsins で取得し activeAsins に union

追加課金: なし。Notion API は無料枠 (3 req/sec rate limit) で十分、Keepa/PA-API/Claude/X/Bluesky の call 数は変動なし (むしろ除外で微減)。

2.5.X 規律の責務分担

  • Bon (user): 恒久ブロック判断 / Notion ブラックリスト DB へのページ追加 / 既存 candidate の rejected 遷移
  • c2 main: COOLDOWN_HOURS 拡張 / queryBlacklistAsins 実装 / orchestrator の union 拡張 / test 追加
  • queryBlacklistAsins: Notion ブラックリスト DB を paging で全取得し ASIN Set を返す (filter なし、全件取得)
  • 既存 loadBlocklist / queryDuplicateAsins / readRecentAsins: 変更なし (1 機能 1 ソースの原則を維持)

3. Non-Goal

  • 既存 data/blocklist.md の廃止: 並行運用する。md は git 履歴で「なぜブロックしたか」が PR レビューに残る価値があり、Notion DB は bon の UI 導線として併用
  • rejected status の意味変更: ADR-003 で「価格再下落時の再候補化を許可」と決めた挙動を維持する。恒久ブロックは 別 DB として実装 (案 A は採用しない)
  • Notion ブラックリスト DB の自動同期 (md ↔ DB): 双方向同期は複雑度に見合わない。bon が必要なら md と DB の両方に手動登録 (運用判断)
  • category / brand 単位の恒久ブロック: 当面は ASIN 単位のみ。category/brand 単位の除外は CATEGORY_QUOTA=0 や WATCH_BRANDS 削除で代替可能
  • cooldown 日数のカテゴリ別差分化: 全 ASIN 一律 30 日。category/source ごとの可変 cooldown は将来検討
  • ブラックリスト追加の slash command / bot UI 化: Notion UI 直接編集で十分

4. Acceptance Scenarios (Gherkin)

4.1 Scenario A1: 30 日 cooldown で同 ASIN が再候補化されない

Scenario A1: 30-day cooldown via COOLDOWN_HOURS=720
  Given COOLDOWN_HOURS = 720 (= 30 日)
  And   ASIN=X が 10 日前に Notion DB に Status=posted で投入されている
  When  cron `npm start` が走る (orchestrator.main)
  Then  queryDuplicateAsins() は X を含む Set を返す
  And   activeAsins.has(X) が true
  And   collectDeals 結果に X が含まれていても filter で除外される
  And   createDraftPage(X) は呼ばれない

4.2 Scenario A2: 31 日経過後は再候補化が許可される

Scenario A2: cooldown expiry
  Given COOLDOWN_HOURS = 720
  And   ASIN=Y が 31 日前に Notion DB に Status=posted で投入されている
  And   Y がブラックリスト DB に登録されていない
  When  cron が走る
  Then  queryDuplicateAsins() の cutoff (now - 720h) より Y の候補生成日時が古い
  And   Y は activeAsins に含まれない
  And   Y が値下げ中なら createDraftPage(Y) で新規 backlog として再投入される

4.3 Scenario A3: Notion ブラックリスト DB の ASIN は永久に除外

Scenario A3: permanent blacklist via Notion DB
  Given NOTION_VUEPRIX_BLACKLIST_DATA_SOURCE_ID が GitHub Actions secrets に設定済
  And   Notion ブラックリスト DB に ASIN=Z のページが存在 (登録日問わず)
  When  cron が走る
  Then  queryBlacklistAsins() が Z を含む Set を返す
  And   activeAsins に Z が union される
  And   deals/fixed/brand いずれの経路で Z が hit しても filter で除外される
  And   1 年経過後 (cooldown 外) でも Z は除外され続ける

4.4 Scenario A4: ブラックリスト DB と blocklist.md は OR で適用

Scenario A4: dual permanent-block sources
  Given ASIN=P1 は data/blocklist.md にのみ存在
  And   ASIN=P2 は Notion ブラックリスト DB にのみ存在
  And   ASIN=P3 は両方に存在
  When  cron が走る
  Then  loadBlocklist() は {P1, P3} を返す
  And   queryBlacklistAsins() は {P2, P3} を返す
  And   いずれの ASIN も最終 targets に含まれない

4.5 Scenario A5: Notion ブラックリスト DB の env 未設定で fail-safe

Scenario A5: missing env var degrades gracefully
  Given NOTION_VUEPRIX_BLACKLIST_DATA_SOURCE_ID が未設定 (空文字 or undefined)
  When  cron が走る
  Then  queryBlacklistAsins() は warn ログを出して空 Set を返す
  And   run は failure にならず success/partial で完了する
  And   既存 blocklist.md / cooldown による除外は通常通り機能する

4.6 Scenario A6: Notion API 失敗時の挙動

Scenario A6: Notion API failure isolation
  Given Notion API が 5xx or timeout を返す
  When  Promise.all 内の queryBlacklistAsins() が reject する
  Then  既存仕様 (queryDuplicateAsins と同じ) に従い orchestrator は fatal として catch
  And   run-log の status = 'failure'
  And   process.exit(1) で cron 失敗を可視化
  # Notion 不通は重大障害として上に伝える方針 (既存 queryDuplicateAsins と統一)

5. Devil's Advocate

5.1 前提は正しいか

前提 1: 「同じ ASIN が 24h で再候補化されるのは害」— 値下げ継続中は本来「再ヒット = 良情報」だが、bon の Notion ワークロード (毎日同じ商品を rejected する手間) が大きく、転換率の高い新規発見が埋もれる害の方が上回ると判断。30 日が適切かは経験則 (一般的にセール周期 = 月 1) で、運用 1 ヶ月後に統計レビューして 14 日 / 60 日に調整可能 (1 行変更)。前提 2: 「Notion UI からブラックリスト登録したい」— bon の運用負荷直接観測。md PR の往復より UI 編集が速いのは明白。

5.2 もっと簡単な代替案はあるか

代替案 A (rejected を恒久化): 既存 DB の rejected ステータスを「2 度と紹介しない」に意味変更。新 DB 不要。却下理由: ADR-003 で「rejected はガイドライン残し + 再候補化許可」と明示しており、破壊的変更になる。さらに「ガイドライン目的の rejected」と「恒久ブロック目的の rejected」を 1 status で表現できず、bon が混乱する。代替案 D (do-nothing + md 拡張): 現状の md 運用のまま、bon に「PR 慣れろ」と促す。却下理由: 運用負荷の根本解決にならない。採用案 B (新 DB) は env var + 関数 1 つ追加で済み、責務分離が明確。

5.3 見落としているリスク・副作用

(1) 30 日 cooldown で MAX_QUERY_PAGES=10 (= 1,000 件) cap 接近: 30 日 × 12 run/day × 最大 30 draft = 理論 10,800 件。実運用では通常 1,000 件未満で収まる想定だが、cap 到達 warn (src/notion.ts:399) は監視必須。Phase 2 で warn 検知時は MAX_QUERY_PAGES = 30 に拡張する増分対応で十分。(2) post-history.jsonl のサイズ膨張: 既に追記のみ運用 (rotation なし) なので、30 日参照では何も変わらない。線形スキャン O(N) で N ≤ 数千件想定、性能問題なし。(3) Notion ブラックリスト DB の整合性: 同一 ASIN を bon が 2 度登録する可能性。queryBlacklistAsins は Set 集約なので副作用なし、ただし bon 視点で混乱するため Notion DB の ASIN property に「重複警告 view」(formula) を推奨運用として doc 化する (実装不要)。(4) 「30 日経過後の再候補化」の挙動が直感に反する場合: 30 日後に同じ ASIN が再 backlog で来ると bon が「あれ、これ前に投稿したやつ」と混乱する。対策: Notion DB の posted 履歴で確認可能、UI 工夫は本 spec の scope 外。

5.4 ユーザー価値 (PM 視点)

動く: cron で 30 日 cooldown と Notion ブラックリストが効く。使える: bon が Notion UI で恒久ブロック登録、開発者 PR レビュー無しで運用可能。使い続けられる: 追加課金ゼロ、env var 1 つ追加のみで運用負荷も増えない。本機能の真の価値は bon の Notion 編集時間削減で、ADR-001 success criteria (月 ¥30-40k) に間接寄与する (運用時間が減れば bot の継続性 = 収益継続)。検証: 1 ヶ月運用後に bon の「rejected 操作回数」減少を観察。

5.5 テスト戦略

Unit test (vitest): (1) notion.test.ts に queryBlacklistAsins の正常系 / paging / env 未設定 / API 失敗ケース追加、(2) orchestrator.test.ts の queryBlacklistAsinsMock 追加して union が正しく実施されることを確認、(3) history.test.ts は cooldown 値変更の影響なし (引数で受ける設計のため)。Integration test: なし (既存方針通り Notion API は live で叩かない)。E2E sanity: DRY_RUN=true 相当で 1 run 実行し、log に activeAsins.union 件数 + blacklist.size が記録されることを目視確認。Manual: bon が DB に 1 件登録して次 cron で除外されるか観察 (acceptance Day 1)。

5.6 既存実装の削除候補はあるか? (zero-base review)

削除候補なし。blocklist.md は git 履歴 + PR レビュー価値で維持、queryDuplicateAsins / readRecentAsins は cooldown 内 race 防御として両立必須 (PR-A3 で意図的に二重化)。本 spec はソース追加のみ、既存ロジック改変なし。refactor 候補: activeAsins の組み立てを「除外ソース配列の reduce」に抽象化する案はあるが、ソース数 4 で抽象化メリット薄。KISS で展開維持。

6.X 設計判断の補足

  • 方式選定: 候補 A (rejected 恒久化) / B (新 DB) / C (md 拡張のみ) のうち B を採用。理由は責務分離 (rejected はガイドライン用、blacklist DB は恒久ブロック用) + bon の Notion UI 導線確保。
  • cooldown 値 = 720h (30 日): bon 主観で「セールサイクル 1 ヶ月」想定。1 ヶ月後の運用観察で 14 日 (336h) / 60 日 (1440h) に再調整可能 (1 行変更)。
  • blocklist.md と Notion blacklist DB の並行運用: 廃止せず併用。md は PR レビューで「なぜブロックしたか」が git に残る、DB は bon の即時運用導線。同期は不要 (取得時に union するだけ)。
  • queryBlacklistAsins の filter: 全件取得 (Status filter なし)。ブラックリスト DB は ASIN 登録の事実 = 恒久ブロック意図、という単純な意味論。Status property は付けない (運用が複雑化するため)。
  • env 未設定時の挙動: queryDuplicateAsins と同じく warn ログ + 空 Set。DRY_RUN / 初期セットアップ時に Notion ブラックリスト DB が未準備でも run は止めない。fail-safe 優先。
  • 失敗時の isolation: queryBlacklistAsins 内例外は orchestrator の Promise.all で reject → fatal catch される (既存 queryDuplicateAsins と同じ位置づけ)。Notion 不通は重大障害として可視化する方針 (Keepa/PA-API と異なり Notion 失敗は run 全体を止める)。
  • category マッピング不要: ブラックリストは ASIN 単位のみ。category 情報は持たせない (検索/集計はする予定なし)。

7. Risks & Mitigations

MED 30 日 cooldown で MAX_QUERY_PAGES=10 cap に接近
発生条件
Notion DB の backlog/doing/approved/posted 件数が 30 日分で 1,000 件を超える
対策
既存の page cap reached warn ログ (src/notion.ts:399) を運用で監視。観測されたら MAX_QUERY_PAGES = 30 に拡張 (1 行)
検証
Phase 1 リリース後 1 週間の run-log に warn 出現確認
ロールバック
COOLDOWN_HOURS を 168 (7 日) 等に縮小して負荷を下げる
MED Notion ブラックリスト DB の env 未設定で機能無効化
発生条件
NOTION_VUEPRIX_BLACKLIST_DATA_SOURCE_ID を GitHub Actions secrets に登録忘れ
対策
fail-safe で空 Set 返却 (run は止めない) + warn ログ。Phase 2 で bon が手順を完了するまでは機能が effectively no-op だが既存 blocklist.md + cooldown は機能
検証
Phase 4 リリース後の最初の run-log で notion blacklist env not configured warn が出ていないことを確認
ロールバック
不要 (no-op フォールバック済)
LOW 30 日 cooldown で「セール継続中の良案件」を取り逃す
発生条件
ASIN=X が 1 ヶ月以上値下げ継続 (例: 在庫処分品)、初回投稿後 30 日間は再投稿されない
対策
bon が手動で当該 ASIN を FIXED_ASINS (config.ts:3) に追加すれば固定 ASIN 経路で継続投稿可能 (cooldown 適用は dedup 経由なので注意)
検証
運用 1 ヶ月後に「逃した案件」を bon の主観で評価、不満なら cooldown を 14 日に短縮
ロールバック
COOLDOWN_HOURS を 24 に戻す (1 行)
LOW Notion ブラックリスト DB の Notion API 失敗で run が落ちる
発生条件
Notion API 5xx / rate limit / network 障害
対策
既存 queryDuplicateAsins と同じく fatal として扱う方針 (Notion 失敗は重大障害として可視化)。@notionhq/client v5 の自動 retry で transient はカバー済
検証
orchestrator.test.ts に Notion 失敗時の run-log status='failure' assertion
ロールバック
Notion 障害が長引く場合は NOTION_VUEPRIX_BLACKLIST_DATA_SOURCE_ID を unset して queryBlacklistAsins を no-op 化
LOW bon がブラックリスト DB に誤って ASIN を登録
発生条件
bon の操作ミスで本来ブロックすべきでない ASIN を登録
対策
Notion DB なので削除も即時可能。次 cron (最大 2h 後) に解除反映
検証
運用ドキュメントに「ブラックリスト追加前に商品名で確認」を明記
ロールバック
Notion DB から該当ページを archive/delete

8. Out of Scope

  • md ↔ Notion ブラックリスト DB の双方向同期: 手動運用で十分、同期実装は複雑度に見合わない
  • category / brand 単位の恒久ブロック UI: CATEGORY_QUOTA / WATCH_BRANDS で代替可能、UI 化は要望次第
  • cooldown 日数のカテゴリ別差分化: 全 ASIN 一律 30 日。category/source 可変 cooldown は将来検討
  • ブラックリスト追加の自動推薦 (e.g. rejected が 3 回続いた ASIN を自動ブラックリスト化): 機械的判断は誤検知リスクあり、bon の主観判断を維持
  • activeAsins 組み立ての抽象化 refactor: ソース数 4 で抽象化メリット薄、KISS で展開維持
  • MAX_QUERY_PAGES の自動拡張: warn 検知時の手動対応で十分
  • Notion ブラックリスト DB の「自動アーカイブ」 (例: 1 年経過したら自動削除): 恒久ブロックの意味から外れる、不要
