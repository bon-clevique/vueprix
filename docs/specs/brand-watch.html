Spec: brand-watch

vueprix bot に「ブランド指定ウォッチ」経路を追加する設計。初期ターゲットは 山﨑実業 / 貝印 / HARIO の 3 ブランド。Keepa Pro €29/月の予算内で完結、追加課金ゼロ。

1. Context (背景)

現状 vueprix bot は以下 2 経路で値下げ商品を検知する:

  • Keepa Deals 経路: 7 カテゴリ (food / health / kitchen / stationery / pc-desk / audio / gaming) を /deal API で巡回
  • 固定 ASIN 経路: FIXED_ASINS に列挙した 9 件を /product API で個別チェック

カテゴリ巡回は「テーマフィット」「価格帯」「title 白リスト」でフィルタするが、特定ブランドの製品だけを追跡する手段がない。bon が「山﨑実業 (tower シリーズ)」「貝印 (関孫六 等)」「HARIO (V60 等)」のような信頼ブランドの値下げを継続的に拾いたいと判断したため、ブランド軸の検知経路を追加する。

調査の結果、Keepa Product Finder API (/query) は公式に brand と manufacturer フィールドを持ち (`keepacom/api_backend` の ProductFinderRequest.java で確認済)、最大 50 個までの OR 検索が可能。トークン消費は現状 10% 程度のため、3 ブランド追加しても予算余裕大。

1.5 Glossary

Product Finder (/query)
Keepa の検索 API。任意フィルタ (brand / manufacturer / 価格範囲 / sales rank 等) で ASIN を絞り込み、ページング (page 0-9, perPage ≤ 50) で取得する。asinsOnly=true で ASIN のみ取得が可能。
Deals (/deal)
既存使用。カテゴリ ID を指定して値下げ商品リストを取得。1 call ≈ 50 トークン。
SavingBasis
PA-API GetItems の Offers.Listings[0].SavingBasis.Amount。Amazon UI の打消し線価格 (定価)。固定 ASIN 経路で reference price 最優先採用。
CATEGORY_QUOTA
カテゴリ別の 1 run あたり draft 上限 (現状合計 20)。Brand 経路は別 quota BRAND_QUOTA で独立管理し、既存枠を圧迫しない設計。
Token Budget
Keepa Pro: 1 トークン/分 × 60 × 24 = 43,200 トークン/日。現状 4,308/日 (10%) 消費。Brand 追加で +360/日 (合計 11%) を見込む。

2. Goal

GitHub Actions cron が 2 時間おきに走るたびに、山﨑実業 / 貝印 / HARIO の各ブランドで 15% 以上値下げしている ASIN を Keepa /query で検出し、既存の Deals 経路と独立した BRAND_QUOTA 枠 (例: 各ブランド 2 件 = 計 6 件/run) に基づいて Notion DB に Status=backlog で投入する。

固定 ASIN と異なり brand hits は数百〜数千件の候補から選別するため、title-whitelist は適用せず (ブランド指定時点でテーマフィット済)、dropPercent 降順で上位 N 件のみ採用する。月額課金は 変動なし (€29/月)。

2.5.X 規律の責務分担

  • Bon (user): ブランド追加判断 / Notion AI で投稿文編集 / Status=approved 遷移
  • c2 main: ブランド検証スクリプトの実装 / config 追加 PR / dry-run 結果確認
  • brand-watch.ts: cron 内で /query 呼び出し + checkAsin 連携 + BRAND_QUOTA 枠選別
  • 既存 draft.ts: 経路統合 (deals/fixed/brand 3 経路の Candidate 集計と Notion 書き込み)

3. Non-Goal

  • Brand hits の 即投稿 (固定 ASIN 経路相当): 投稿文を Notion AI で生成する標準フロー (Status=backlog → approved) に揃える
  • SNS への投稿先追加 (Mastodon / Threads 等)
  • ブランド別 Notion カテゴリの新設 (既存 kitchen 等の category へ流す。new brand-list category は最小実装としては不要)
  • 機械学習による「人気ブランド自動発見」 (運用で手動 curate)
  • Amazon ブランドストア API 連携 (Keepa Product Finder で十分)
  • brand 表記の自動正規化 (dry-run スクリプトで bon が手動確認する運用)

4. Acceptance Scenarios (Gherkin)

4.1 Scenario A1: 3 ブランドの値下げを検出して Notion へ投入

Scenario A1: brand-watch end-to-end via cron
  Given KEEPA_API_KEY と NOTION_API_KEY が GitHub Actions secrets に設定済
  And   WATCH_BRANDS=["山崎実業", "貝印", "HARIO"]
  And   BRAND_QUOTA=2 (各ブランド)
  When  cron `npm run draft` が走る
  Then  Keepa /query が 1 回呼ばれる
  And   各ブランドで 15% 以上値下げ ASIN が candidates に入る
  And   Notion DB に最大 6 件 (3 × 2) の draft が Status=backlog で作成される
  And   run-log にも brand 経路の件数が記録される

4.2 Scenario A2: brand hits が既存 Deals/Fixed と重複しない

Scenario A2: dedup with existing routes
  Given 既存 deals 経路で ASIN=X が既に candidates に入っている
  And   同じ ASIN=X が brand 経路でも hit する
  When  draft.ts main() が走る
  Then  Notion DB の queryDuplicateAsins / blocklist フィルタで重複が除去される
  And   draft は 1 件のみ作成される (source 列は最初に検出した経路を記録)

4.3 Scenario A3: トークン予算内で完結

Scenario A3: token budget under 15% per day
  Given 現状の Deals + Fixed で 4,308 token/day 消費 (10%)
  When  Brand 経路を追加して 1 日 12 runs 走らせる
  Then  Brand 経路の追加消費が 1 日 ≤ 500 token (1%)
  And   合計 token 消費が ≤ 4,808/day (≤ 12%)
  And   月額課金は変動なし (Keepa Pro €29 内)

4.4 Scenario A4: ブランド表記揺れの dry-run 検証

Scenario A4: brand name verification
  Given verify-keepa-brand.ts スクリプトが存在する
  When  `tsx scripts/verify-keepa-brand.ts "山崎実業" "Yamazaki"` を実行
  Then  各表記の hit 数と sample title が標準出力に出る
  And   hit 数 0 の表記は WATCH_BRANDS に含めない判断材料となる

4.5 Scenario A5: brand 経路が失敗しても他経路は止まらない

Scenario A5: failure isolation
  Given Keepa /query が 5xx や timeout で失敗する
  When  draft.ts main() が走る
  Then  brand-watch の例外は warn ログのみで catch される
  And   Deals 経路と Fixed 経路は通常通り完了する
  And   run-log の status は 'partial' か 'success' (failure ではない)

5. Devil's Advocate

5.1 前提は正しいか

前提「特定ブランドの値下げを追えば収益率が上がる」は未検証。bon の主観 + 一般論 (信頼ブランドは転換率が高い) が根拠。本実装後 1 ヶ月で brand 経路の投稿転換率を Keepa Deals 経路と比較する KPI 検証を行う ことで前提検証する。検証が NG なら ADR-002 を起こして撤去判断する。

5.2 もっと簡単な代替案はあるか

代替案 C (Deals + title-filter): 既存 getDeals 結果から title に「山崎実業 / Yamazaki / KAI / 貝印 / HARIO」を含む ASIN だけ拾う実装。コード追加 ~10 行、新 API 不要。短所: ブランド表記揺れ (山﨑/山崎/Yamazaki) に脆弱 + カテゴリ巡回内に限定。do-nothing 案: 固定 ASIN を bon が手動追加する (現状運用)。本 spec の方式 B (Product Finder) を採るのは「将来のブランド追加コストを 1 行 config 編集に下げる」ためで、初期 3 ブランドだけなら代替案 C で十分という反論あり。判断: B を採用、ただし Phase 1 では brand 経路の hit 件数を log に残して C との比較材料にする。

5.3 見落としているリスク・副作用

(1) ブランドストア外品の混入: brand=山崎実業 で hit する商品に「山崎実業の OEM 互換品 (非公式)」が混じる可能性。Amazon の brand registry を Keepa がどこまで尊重するかは未検証 → Phase 1 で sample 100 件目視確認。(2) scope drift: 山﨑実業の主力は収納/雑貨で ADR-001 の「食・健康・生活の質」テーマからやや外れる。WATCH_BRANDS 追加は ADR 必須化の規律で防御。(3) title-whitelist スキップ: brand 経路は whitelist を通さないので、本来テーマ外の商品も流れ込みうる → Notion 手動承認で防御するが防御がガバいなら brand-specific title-deny-list を追加する。

5.4 ユーザー価値 (PM 視点)

動く: cron で hit を取れる。使える: Notion AI で文言生成して投稿できる。使い続けられる: 月額固定 €29 で運用変動なし。本機能の真の価値は ADR-001 success criteria (月 ¥30-40k) に直接寄与するか で、bon の「信頼ブランドの転換率が高い」仮説が当たれば寄与する。仮説検証は Acceptance 後 1 ヶ月の brand 経路 vs deals 経路の click-through 比較で実施。

5.5 テスト戦略

Unit test (vitest): brand-watch.ts の parseBrandHit / selectByBrandQuota / dedupe を mock Keepa response でカバー。Integration test: なし (Keepa API は live で叩く dry-run スクリプトで代替)。E2E sanity: DRY_RUN=true 相当の検証スクリプトを GitHub Actions 手動 dispatch で走らせて Notion 投入を観測。Manual sanity (non-blocking): 3 ブランドの sample 5 件を目視で「ブランド整合 + テーマ整合」を確認。

5.6 既存実装の削除候補はあるか? (zero-base review)

削除候補なし。本機能は新規経路の追加で、既存 Deals / Fixed のロジックを置換しない。ただし、collectFixed / collectBrandHits / collectDeals の 3 関数で重複する Candidate 生成 + Notion 投入の共通化 は今後の refactor 候補 (本 spec の scope 外、Plan の Out of Scope に記載)。今は KISS で 3 経路並列を維持。

6.X 設計判断の補足

  • 方式選定: 候補 A (Brand Search) / B (Product Finder) / C (Deals + post-filter) の中で B を採用。理由は Keepa 公式 brand インデックスで表記揺れ吸収 + サーバ側 value filter (deltaPercent90, current_AMAZON) で無駄 token 圧縮。
  • BRAND_QUOTA 分離: 既存 CATEGORY_QUOTA (合計 20) を圧迫しない別枠。初期値は brand あたり 2 件 = 6 件/run。MAX_POSTS_PER_RUN=30 枠内に十分収まる。
  • Notion category マッピング: brand hits は固定的に kitchen へ流す (3 ブランドとも実用品で kitchen がもっとも近い)。新 category brand-list 作成は Phase 1 では避け、Notion 運用が乱れたら次 PR で追加検討。
  • title-whitelist 適用判断: brand 経路では 適用しない。ブランド指定時点でテーマフィット済とみなし、白リスト不一致を理由に drop しない。乱用が観測されたら brand-specific deny-list を導入。
  • 失敗時の isolation: collectBrandHits 内例外は warn ログのみで catch、既存 Deals/Fixed 経路の処理は継続。run-log の status は brand 失敗単独では partial に降格しない (deals/fixed が成功していれば success)。

8. Out of Scope

  • collectDeals / collectFixed / collectBrandHits の共通化 refactor: 3 経路の Candidate 生成を抽象化する作業。本 PR では KISS で並列維持、refactor は別 PR で検討
  • ブランド別 Notion category の新設 (例: brand-yamazaki): Phase 1 では既存 kitchen へ流す。乱用観測時に category 分離検討
  • brand 経路の即投稿化 (固定 ASIN 相当): 現時点では Notion AI 経由 (Status=backlog → approved) で十分。即投稿は将来検討
  • brand を超えた「manufacturer 軸ウォッチ」: 当面 brand のみで対応、manufacturer 追加は Phase 2 以降の拡張
  • brand 経路の click-through KPI 計測ダッシュボード: 1 ヶ月後に bon が手動集計 (Notion DB の posted カウント比較)、ダッシュボード化は要望次第
